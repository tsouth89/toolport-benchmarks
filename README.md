# toolport-benchmarks

A reproducible, one-command benchmark of the **standing input-token cost** of
having MCP tools available, with and without [Toolport](https://toolport.app)'s
lazy discovery. Benchmarks or it didn't happen: everything runs from committed
fixtures with a deterministic local tokenizer, no API keys or network required.

```bash
npm i && npm run bench
```

## What it measures

The standing INPUT-token cost a model pays just to have tools *available* on
every request, two ways:

- **Full mode (baseline):** the client injects the entire MCP `tools/list`
  (every tool's `name` + `description` + `inputSchema`) into the model's context
  on every turn. Cost = tokens of that serialized tool array.
- **Lazy mode (Toolport):** the client injects ONLY Toolport's few lazy meta-tools.
  The model searches for and calls real tools on demand. Cost = tokens of those
  meta-tool definitions.

**Headline metric:** standing-context reduction = `(full - lazy) / full`, per
server catalog.

## Results

Generated by `npm run bench` on the committed fixtures. Tokenizer: tiktoken
`o200k_base` (GPT-4o / GPT-5 family). The lazy meta-tool set is constant at
**781 tokens** regardless of how many downstream tools exist.

| Catalog | Tools | Full tokens | Lazy tokens | Standing reduction |
|---|--:|--:|--:|--:|
| Stripe | 587 | 415,391 | 781 | 99.8% |
| GitHub | 1194 | 351,579 | 781 | 99.8% |
| OpenAI | 242 | 299,654 | 781 | 99.7% |

The canonical machine-readable output is `results/benchmark.json`; the rendered
table is `results/benchmark.md`. Both are committed.

## Honesty caveat (read this)

This is the **standing** context cost, the tokens tools occupy on *every*
request just by being available. It is not an end-to-end session saving.

Lazy mode adds **per-search result tokens**: when the model calls
`toolport_search_tools`, the search returns a handful of matching tools' schemas
as a tool *result*, and those tokens are paid once per search. So:

- The **standing reduction** (the table above) is the honest headline: a Stripe
  user pays 781 tokens of always-on tool context instead of 415k.
- The **amortized** savings for a real session depends on how many DISTINCT
  tools that session actually touches. A session that ends up using 30 different
  Stripe tools pays for ~30 tools' worth of search results, still far below
  loading all 587 on every turn, but not the full 99.8%.

We report the standing reduction and state this plainly. We do not claim the
headline percentage as a whole-session saving.

## Why the percentage is the robust number

Absolute token counts differ ~10-15% between tokenizers (Claude and Gemini
tokenize JSON slightly differently than `o200k_base`). But both the full catalog
and the lazy meta-tools are JSON of similar character, so a tokenizer shift
scales both sides almost identically and the **reduction percentage is
near-invariant**. That is why we lead with the % and treat `o200k_base` counts as
representative rather than absolute.

Optional exact Claude cross-check: if `ANTHROPIC_API_KEY` is set, `npm run bench`
also calls Anthropic's `/v1/messages/count_tokens` on the hero (first) catalog
and records the Claude full/lazy counts and their reduction in
`results/benchmark.json` (`claudeCrossCheck`). It is skipped silently with no key
so the deterministic run never depends on network or credentials.

## Fixtures (all REAL, none hand-written)

### The lazy meta-tool set: `fixtures/toolport-lazy-tools.json`

The exact tool definitions Toolport advertises in lazy mode by default. Extracted
verbatim from the gateway source:

- **Source:** the Toolport app repo, `src-tauri/src/bin/conduit-gateway.rs` (the
  gateway binary keeps the name `conduit-gateway` for upgrade compatibility).
- The individual definitions are the `status_tool_def()`, `search_tool_def()`,
  `call_tool_def()`, and `fetch_result_tool_def()` functions.
- The assembly that decides the DEFAULT lazy `tools/list` is the `if lazy { ... }`
  block, which pushes exactly these four:
  `toolport_status`, `toolport_search_tools`, `toolport_call_tool`,
  `toolport_fetch_result`.
- Three more meta-tools exist but are **conditional**, so they are NOT in the
  default set and NOT counted here: `toolport_enable_server` /
  `toolport_disable_server` (only when the user opts into agent control) and
  `toolport_confirm` (only when destructive-confirmation is on). Including them
  would only make lazy mode look slightly larger; we benchmark the default.

### Server catalogs

Each `*.tools.json` is a real MCP `tools/list` array (`{ name, description,
inputSchema }` per tool), generated with the exact
[`toolport-openapi-mcp`](https://github.com/tsouth89/toolport-openapi-mcp) logic
(`loadApi`) pointed at a real, public OpenAPI spec. `toolport-openapi-mcp` maps
one MCP tool per API operation: `operationId` -> tool name, parameters + request
body -> input schema. This is what a client would actually receive from that
server.

| Fixture | Tools | Spec source |
|---|--:|---|
| `fixtures/stripe.tools.json` | 587 | `raw.githubusercontent.com/stripe/openapi/master/openapi/spec3.json` |
| `fixtures/github.tools.json` | 1194 | `raw.githubusercontent.com/github/rest-api-description/main/descriptions/api.github.com/api.github.com.json` |
| `fixtures/openai.tools.json` | 242 | `raw.githubusercontent.com/openai/openai-openapi/master/openapi.yaml` |

Stripe is the hero (the 587-tool count matches toolport-openapi-mcp's own README
claim). GitHub and OpenAI show the reduction holds across catalog sizes.

To regenerate a fixture yourself: build `toolport-openapi-mcp`
(`npm i && npm run build`), then run its `loadApi(specUrlOrPath, {})` and write
`api.tools.map(t => ({ name: t.name, description: t.description, inputSchema:
t.inputSchema }))` to the fixture path. (The committed fixtures already contain
this; no regeneration is needed to reproduce the numbers.)

## How token counting works

- Each side's cost is `tiktoken.encode(JSON.stringify(tools))` with the
  `o200k_base` encoding, i.e. the token length of the serialized tool array as it
  would sit in context. Both the full catalog and the lazy meta-tools are
  serialized the same compact way, so array framing is counted identically,
  apples to apples.
- Special-token handling is disabled during encoding, so a literal `<|endoftext|>`
  appearing inside a tool description (some specs contain it) is counted as
  ordinary text rather than a control token.

For reference, Toolport's own in-app "tokens saved" counter uses a cruder
`chars / 4` estimate (it avoids bundling a tokenizer into the gateway). This
benchmark's tiktoken counts land within ~7% of that estimate on these catalogs,
and the reduction percentage is identical to one decimal either way.

## Recall: can lazy discovery still find the tool?

Cutting the standing cost only helps if the agent can still *find* the right tool
on demand. This benchmark runs Toolport's **real** lexical ranker (the same
`search_catalog` the gateway serves `toolport_search_tools` from, not a
re-implementation) over the 587-tool Stripe catalog against 23 paraphrased,
gold-labelled intents (e.g. "refund a payment" -> `PostRefunds`, "close a
dispute" -> `PostDisputesDisputeClose`), and reports recall@k: how often the
correct tool lands in the top k results.

| recall@5 | recall@10 | recall@25 |
| --: | --: | --: |
| 91% | 96% | 100% |

Run it (the harness lives in the gateway repo so it exercises the shipping ranker):

```bash
# from the toolport gateway checkout
STRIPE_TOOLS_JSON=../toolport-benchmarks/fixtures/stripe.tools.json \
STRIPE_INTENTS_JSON=../toolport-benchmarks/fixtures/stripe.intents.json \
RECALL_SERVER= \
  cargo test --manifest-path src-tauri/Cargo.toml --bin toolport-gateway \
  recall_report -- --nocapture
```

The intents are ours (a labelled set, stated plainly). The same harness accepts
any `[{name, description, inputSchema}]` catalog plus `[{q, ok}]` intents, so a
recognised public set such as the [MCP-Zero](https://github.com/xfey/MCP-Zero)
`mcp-tools` dataset (2,797 tools) drops straight in once converted to that shape.
